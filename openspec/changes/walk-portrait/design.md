## Context

`WalkHistoryScreen.tsx` renders a flat `FlatList` of `StoredWalk`s (`repository.getWalks()`), each row showing date, a closed/qualifying status word, and a point count. Rows aren't tappable to anything. `StoredWalk` (`src/storage/WalkRepository.ts`) is `Walk & { syncedAt: number | null }`; `Walk` (`src/types.ts`) has `id`, `startTime`, `locations: Location[]`, `closed: boolean`, `startSource: 'button' | 'manual-log'` — nothing else. A manual log always has `locations: []`.

Two already-built (unarchived) changes matter directly here:
- `home-dashboard` built `TerritoryPortrait.tsx` + `src/web/portraitHTML.ts`: a hidden WebView that fetches OSM tiles for a raster's bounding box, draws them onto an offscreen canvas at the pixel position Leaflet's own projection math says they belong, composites `renderHomeRangePortrait`'s fill+outline output on top, and calls `canvas.toDataURL()` once — producing exactly one static image. It is not, and cannot cheaply be made into, an animatable view; it's a one-shot export pipeline.
- `somewhere-wild` built `src/utils/streetLookup.ts` (`resolveLabelForPoint`, private; `resolveWildClusterLabel`/`resolveNewGroundSpot`, exported and shaped for its own two use cases) and extended `HomeRangeRepository` with a singleton `NewGroundEvent` (`occurredAt`, `cellIds`) — overwritten on every new discovery, carrying no walk id and no location of its own.

This document assumes `proposal.md`'s scope as settled and answers the concrete "how" questions it flagged, most importantly the draw-on-animation feasibility call.

## Goals / Non-Goals

**Goals:** land Walk Portrait as a presentation layer with zero new economy/mechanic logic; reuse `mapHTML.ts`'s already-verified live Leaflet+tile+bridge pattern and `homeRangeRendererScript.ts`'s already-verified blur/LUT/contour math rather than inventing a second rendering technique; reuse `home-dashboard`'s `TerritoryPortrait` directly wherever a static image is actually the correct answer, not wherever it's merely convenient; make every new persisted field additive and backward-compatible (existing rows must still parse and degrade gracefully).

**Non-goals:** anything on the brief's explicit "never build" list (pace/speed coloring, rankings, comparison view, share/export, coverage-gap highlighting) or its "deferred" list (pinch-zoom/pan, time-scrubbing, historical wildness reconstruction, list-row thumbnails) — see `proposal.md`. Backfilling New Ground data for walks saved before this change ships — not possible from what's stored (see Decision 4), and not attempted.

## Decision 1 — The draw-on animation: feasible, but not via the render-to-image path

**The concept's own assumption (reuse `TerritoryPortrait.tsx`/`portraitHTML.ts`) is the wrong mechanism for this requirement, and is superseded here — not silently, per the brief's explicit instruction to flag this rather than ship static.**

`portraitHTML.ts`'s pipeline (fetch every OSM tile the bounding box needs → draw each onto an offscreen canvas at its projected pixel position → composite the Home Range overlay on top → one `canvas.toDataURL()` call) produces a single image per invocation. Animating a 1.2s trail reveal on top of that would require re-running some or all of that pipeline 30-70 times (at ~20-70ms per frame budget for perceived smoothness) — each capture involves canvas compositing and, if tiles aren't already loaded, network fetches. That's not "slow," it's structurally the wrong shape: this pipeline exists to produce one still image, not a video.

**Correct approach: don't export anything for this state.** Build a new, dedicated WebView — `src/web/walkPortraitHTML.ts` — modeled directly on `mapHTML.ts`'s already-shipped live map (tiles via `L.tileLayer`, `renderHomeRangeToMap`'s layer-group pattern, `L.polyline` for a trail, `L.marker`/`L.divIcon` for markers, the same dual `window`/`document` `message` listener convention), except:
- Never pannable/zoomable/interactive (`dragging: false, touchZoom: false, scrollWheelZoom: false, doubleClickZoom: false, boxZoom: false, keyboard: false, zoomControl: false` on the `L.map(...)` constructor — this map **is** visible on screen, unlike `portraitHTML.ts`'s hidden one, so every gesture needs to be explicitly turned off, not just visually hidden).
- Fed one message (`RENDER_WALK { walkLatLngs, newGroundCellIds, raster }`) instead of a live-updating GPS stream.
- The trail reveal is a JS animation loop *inside the WebView* that grows the coordinate array passed to `L.polyline.setLatLngs()` over ~1.2s (`requestAnimationFrame` or `setInterval`, implementer's call) — cheap, native-canvas-backed Leaflet redraw, no per-frame export, no network round-trip per frame. This is the same primitive `UPDATE_TRAIL` already exercises today for a live walk, just driven by a timer instead of GPS callbacks.
- Offline/slow-tile behavior is **not a new risk this change introduces** — it's the same accepted behavior the live map (`MapView.tsx`) already has (`CLAUDE.md`: "Requires internet access at walk time"). No `PORTRAIT_FAILED`-style handshake is needed here, unlike `portraitHTML.ts` — Leaflet's own tile layer already tolerates missing/slow tiles by showing blank tile squares, exactly as it does on the live map today.

**Two-phase reveal, to satisfy the brief's "New Ground segments should finish drawing last" on top of "start to finish":** these two instructions are only reconcilable if New Ground segments are drawn out of chronological order. Resolved as: Phase A (~70% of the 1.2s) reveals the full trail chronologically in the base color; Phase B (~30%) then colors in just the New Ground segments (already fully present as base-color line by that point) to the brighter green. Both phases still read as "the trail drawing on," and New Ground genuinely finishes last regardless of where in the walk it chronologically occurred. The 70/30 split is a first-pass, easily-retuned implementer number, not a logged balance threshold.

**What's still reused, not reinvented:** `homeRangeRendererScript.ts`'s blur/color-LUT/marching-squares math (Decision 2), the exact tile-layer setup `mapHTML.ts` already has, and `TerritoryPortrait`/`portraitHTML.ts` themselves — reused as-is, unmodified, for the one state where a static capture is actually correct (Decision 2's fallback case). Nothing about `home-dashboard`'s code needs to change for this change to ship.

## Decision 2 — Two distinct rendering states, not one path stretched to cover both

The brief's item 7 describes two visually and narratively different things, and conflating them into one rendering path would misrepresent both:

- **Walk-trail state** (a tracked walk, or a manual log with a linked/refreshed route — see Decision 6): the new live, animated `walkPortraitHTML.ts` WebView from Decision 1. Muted Home Range *behind* a specific, animated trail, fit to that walk's own bounds. This is "this walk, inside everything."
- **No-trail fallback state** (a manual log with no linked route): there is no walk-specific trail to animate — the brief's own copy for this state ("here's everywhere Buddy knows") describes the *aggregate* Home Range, centered, calm, with no motion implied. **This reuses `home-dashboard`'s `TerritoryPortrait` component directly, unmodified**, wired with a no-op `onPress` (it's not a doorway to the map here) — the exact same static, already-verified, already-failure-handled rendering `home-dashboard` built, for the one state it's actually the right tool for. If the Home Range is *also* empty (a brand-new player who has only ever manually logged walks with no route to refresh), `TerritoryPortrait` already renders nothing for `cells.length === 0` — `WalkPortraitScreen` shows the same "hasn't marked the map yet" fallback copy `DoorstepScreen` already uses for its own equivalent empty state, not a new voice.

`WalkPortraitScreen.tsx` picks between these two render paths based on whether `refreshedRouteWalkId` (Decision 6) resolves to a real, still-present route walk — never both, never a third "loading, might be either" flash state beyond the ordinary async-fetch-then-render one every other screen in this codebase already has.

## Decision 3 — Muted Home Range background: a new renderer variant, zero new hex colors for the trail, one new formalized token for the background fill

`renderHomeRangeToMap` and `renderHomeRangePortrait` both draw the fresh→wild Lab-interpolated color LUT — exactly the "wildness colour" the brief wants muted *out* for this screen's background context layer. **Add `renderHomeRangeMuted(map, payload, previousLayerGroup)`** to the same script string (a third sibling, same signature/layer-group-return convention as `renderHomeRangeToMap`, reusing the identical blur → marching-squares pipeline) — flat single-tone fill and outline, no gradient, no wild-ground contour pass, no marker, at reduced opacity.

**Trail colors need zero new tokens**: base trail = `HR_WILD_HEX` (`#DCE8BE`, the existing "Wild meadow" Design Token) — pale green; New Ground segments = `HR_FRESH_HEX` (`#2ECC71`, the existing "Primary green" Design Token) — bright green. This satisfies "brighter green than the rest of the trail" literally, using colors already in the token list.

**The muted background fill does need one new token.** The natural "muted grey-green" is `#8A9A8A` — already used informally throughout this codebase (`WalkHistoryScreen.tsx`'s `COLORS.muted`, `TerritoryPortrait.tsx`'s fallback text) as ad hoc UI text color, but never added to `visual-design/spec.md`'s official Design Tokens list, and never used as a *map-rendering* color before. Per `CLAUDE.md`'s own rule ("No new colors without updating that spec's Design Tokens list and explaining why"), this change formalizes it: adds "Muted grey (context/background chrome)" to the Design Tokens list via this change's own `specs/visual-design/spec.md` delta, rather than quietly reusing an unofficial color for a new purpose. This also retroactively documents its existing informal use, closing a small pre-existing gap rather than compounding it — noted, not silently fixed beyond this one addition (no drive-by re-theming of `WalkHistoryScreen.tsx`'s existing `COLORS.muted` usages).

## Decision 4 — New Ground segments: new per-walk persistence, not a query-time recomputation

**Not recoverable from what's already stored, for any walk other than possibly the single most recent New-Ground-producing one.** `HomeRangeRepository.getLastNewGroundEvent()` is a singleton row (see `somewhere-wild/design.md` Decision 4) — overwritten by every subsequent discovery, and it carries no `walkId`, only `occurredAt`/`cellIds`. A `Cell` record (`HomeRangeRepository.ts`) has `lastRefreshed`/`lastTracked`/`visits` but no "first ever painted at" timestamp — there is no field anywhere that answers "was this cell new at the moment walk X painted it" after the fact.

**The data does already exist, once, in memory, at the moment it matters — it's just discarded today.** `App.tsx`'s `finishWalk` already computes `const newGround = newGroundCells(painted, rangeBeforeSet)` (a `Set<CellId>`) *before* painting and *before* `walkRepository.saveWalk(finishedWalk)` — the exact same value the persisted `NewGroundEvent` is built from, moments later. **Add `newGroundCellIds?: string[]` to `Walk`** (`src/types.ts`), set to `Array.from(newGround)` on `finishedWalk` before that same `saveWalk` call — no new computation, only a new write of an already-computed value, mirroring exactly how `somewhere-wild`'s own task 4.2 added the `NewGroundEvent` write at this identical call site. A manual log's `newGroundCellIds` is always `[]` or omitted (structurally cannot discover new ground, per `walkRewards.ts`'s own existing convention for `newGroundCellCount`).

**Rendering:** a new pure function in `src/utils/grid.ts` — `splitTrailByNewGround(locations, newGroundCellIds): { color: 'base' | 'new-ground'; points: Location[] }[]` — walks the ordered `locations` array once, maps each point to its cell via the already-exported `cellForLocation`, and emits contiguous same-color runs. `walkPortraitHTML.ts` renders one `L.polyline` per run (Leaflet has no native per-segment-color single-polyline API), colored per Decision 3.

**Historical walks get no highlight, gracefully, by construction.** A walk saved before this change ships has `newGroundCellIds === undefined`; `splitTrailByNewGround` treats a missing/empty array as "everything is 'base'," which is exactly the brief's own "if a walk had zero New Ground, the trail renders uniformly" rule — no special-casing needed for "old walk" vs. "walk that genuinely had none."

## Decision 5 — Treats earned, distance, duration: one new field, two derived-on-demand

**`treatsEarned`: new field, because it's genuinely never persisted today.** `awardWalkRewards` (`src/economy/walkRewards.ts`) returns `celebration.treatsEarned`, shown once by `CelebrationScreen` and then gone. **Add `treatsEarned?: number` to `Walk`.** Both `App.tsx` call sites (`finishWalk`, `logMissedWalk`) already save the walk *before* calling `awardWalkRewards` (ordering is load-bearing elsewhere — `walkOrderForDay` counts already-saved closed walks by id, excluding the current one, so the walk must already exist in the repository when rewards are computed). **Add one second `walkRepository.saveWalk({ ...finishedWalk, treatsEarned: result.celebration.treatsEarned })` call, in each site's existing `try` block, right after `awardWalkRewards` resolves.** `saveWalk` is already an upsert (`sqliteWalkRepository.ts`'s `ON CONFLICT(id) DO UPDATE`) — this is a safe, idempotent patch, not a new storage mechanism. A walk that never qualified for a reward (`!qualifies`, `finishWalk`'s early return) never gets this second save and simply has no `treatsEarned` — fine, since it has no metadata row to show one in anyway (non-qualifying walks aren't the ones Walk Portrait's reward-earning framing is built around, though they still get a portrait per the brief's row-tap-always-works rule).

**Distance and duration: derived on demand, never persisted, matching this codebase's existing preference.** `xpAwardForWalk`'s own doc comment in `walkRewards.ts` already states the precedent explicitly: "there is no longer a stored per-walk area to read... recomputed from each prior walk's own recorded trail." Distance is `cumulativeDistance(walk.locations)` (already exported, already used everywhere else this way); duration is `locations[locations.length - 1].timestamp - locations[0].timestamp` (every `Location` already carries a `timestamp`) — no new field, no new storage, one new tiny derivation the implementer writes directly in `WalkPortraitScreen.tsx` (not worth its own utility function for a two-line subtraction, though `cumulativeDistance` is reused as-is).

**The manual-log-with-no-linked-route case has neither**, structurally (`locations: []`). Resolved (flagged in `proposal.md` as needing a quick game-master nod, not blocking): metadata row shows date + treats earned only in that state; the full row (date, distance, duration, treats earned) — sourced from the **linked route's** `locations`, not the manual log's own — for every other state, including a manual log *with* a linked route.

## Decision 6 — Manual-log route-refresh linkage: new field, set where the refresh is already applied

**Not persisted today, contrary to what might be assumed from the mechanic already existing.** `App.tsx`'s `logMissedWalk` receives `refreshRouteWalkId` as a plain function argument, uses it once to paint the picked route's cells with a refreshed timestamp, and then it's gone — nothing on `manualWalk` (the `Walk` object that gets saved) records which route, if any, was picked. `eligibleRefreshRoutes` (`src/utils/manualWalkLog.ts`) only filters *candidates for the picker*, unrelated to remembering the outcome.

**Add `refreshedRouteWalkId?: string` to `Walk`.** Set it on `manualWalk` at the same point `refreshApplied` becomes `true` in `logMissedWalk` (the existing `if (quota.canRefreshRoute && refreshRouteWalkId) { ... }` block), via the same kind of second `saveWalk` patch as Decision 5's `treatsEarned` (both can be one combined second save, not two separate round-trips, since they resolve at nearby points in the same function).

**Dangling-reference edge case, must be handled, not assumed away:** `WalkRepository.deleteWalk` (already shipped, used by `WalkHistoryScreen`'s existing Delete action) can remove the walk a `refreshedRouteWalkId` points at, at any later time, with no cascade or referential check (matching `walk-history/spec.md`'s existing "deleting a walk removes only that walk's own record" rule — this is consistent with existing behavior, not a new violation of it). `WalkPortraitScreen`'s lookup (`walkRepository.getWalk(refreshedRouteWalkId)`) must treat a `null` result as "no linked route" and fall through to Decision 2's fallback state — never a broken reference, never an error string. This needs an explicit scenario in the `walk-storage` spec delta (below) so it isn't lost as an implicit assumption.

## Decision 7 — Reverse-geocoding: export the existing point-resolver, no new wrapper logic

`streetLookup.ts`'s exported functions (`resolveWildClusterLabel`, `resolveNewGroundSpot`) are shaped for their own specific inputs (a `WildCluster`, a `NewGroundEvent`) and both internally delegate to a private `resolveLabelForPoint(latitude, longitude): Promise<string | null>` that already does exactly what Walk Portrait needs: resolve one point, with the same in-memory `labelCache`/`resolveCached` memoization, the same "never throws, `null` means render nothing" contract. **Export `resolveLabelForPoint` directly** (or add a one-line named re-export/wrapper if the implementer prefers not to widen that function's existing name into a more general-sounding public API — a naming-only judgment call, not a logic one). No new geocoding code.

**Point chosen: the walk's own start location** (`locations[0]`, or the linked route's `locations[0]` for a manual log — never a computed centroid, which would need new geometry math for no clear benefit and doesn't match the concept's own emphasis on the start point via the paw marker). Cache key: `walk-portrait:${walk.id}` (or the linked route's id, for a manual log), consistent with the existing cache's per-feature keying convention (`cluster.anchorCellId`, `new-ground:${event.occurredAt}`). The no-linked-route fallback state has no single point to geocode and shows no place-anchored title line at all — matching the brief's own example copy for that state, which doesn't include one.

**New: a time-of-day phrase.** Nothing in this codebase currently buckets an hour into "morning"/"afternoon"/"evening" (`SomewhereWildCard.tsx`'s `dayPhrase` only gives a day-of-week). Add one small pure function — e.g. `dayAndTimeOfDayPhrase(timestamp): string` returning `"Tuesday morning"` etc. — to `src/utils/manualWalkLog.ts`, alongside the file's existing calendar helpers. Exact hour-bucket boundaries are an implementer-level polish call, not a logged balance threshold. **This is the fourth generic calendar/time helper to land in a file literally named for manual-log scope** (`calendarDayKey`, `startOfLocalDay`, `calendarDayGap` already live there per `home-dashboard/design.md`'s own already-logged flag on this exact point) — restated here, not fixed here, per that flag's own explicit "not this change's job to do that rename as a drive-by."

## Decision 8 — Where the new screen's state lives: a top-level `App.tsx` slot, not screen-owned nested state

`CLAUDE.md`'s own architecture note ("all state in `App.tsx` via `useState`/`useRef`") and every prior change's own choice (`showDoorstep`, `showLogMissedWalk`, `showStats`, etc., plus the nullable-object `celebration`) establish a single, consistent pattern: every full-screen surface is a top-level `App.tsx` state slot, never a screen-owned nested modal. Introducing a `viewingWalk`-shaped state *inside* `WalkHistoryScreen.tsx` instead would be the first exception to that pattern anywhere in this codebase, and a fresh agent reading `App.tsx`'s screen chain would have no reason to expect a rendered surface hiding one level down.

**Add `viewingWalk: StoredWalk | null` to `App.tsx`**, mirroring `celebration`'s existing nullable-object convention (not a new boolean paired with a separately-tracked walk) — set via a new `onSelectWalk: (walk: StoredWalk) => void` prop passed to `WalkHistoryScreen`, cleared by `WalkPortraitScreen`'s own close action. Rendered in the screen chain so it takes precedence while `showHistory` remains `true` underneath (dismissing the portrait returns to the still-mounted history list, not the map) — same "overlay while the state beneath persists" shape `celebration` already has over the map screen today. `WalkHistoryScreen` also newly receives a `homeRangeRepository` prop (for the muted background layer and the no-linked-route fallback's `TerritoryPortrait` reuse), passed straight through from `App.tsx`'s existing `homeRangeRepository` instance — no new repository, no prop drilled further than one level.

## Noted, not fixed here

- The pre-existing informal use of `#8A9A8A` as UI text color elsewhere in this codebase predates this change and isn't retroactively migrated to the newly-formalized token name — only its *new* use here (as a map-rendering fill/outline color) is covered by the Design Tokens addition.
- `manualWalkLog.ts`'s growing scope beyond its literal name (flagged again in Decision 7) — not renamed here, per the standing precedent of not doing that rename as a drive-by inside an unrelated change.

## Risks / Trade-offs

- **[New Ground highlighting is permanently unavailable for any walk saved before this change ships]** — accepted, not fixable retroactively; degrades to "uniform trail," which is already a defined, non-broken state per the brief's own rules.
- **[Two second-`saveWalk` patches (Decisions 5 and 6) add a small new failure mode: rewards/refresh apply successfully but the metadata patch write fails]** — low risk (the same upsert path every walk save already uses, already wrapped in each call site's existing `try`/`catch`), but worth its own test coverage per `tasks.md`, since a failed second save would silently leave a walk missing its `treatsEarned`/`refreshedRouteWalkId` with no user-visible error — acceptable (the metadata row/trail-linkage would just be absent, not wrong), but should be logged via the existing `log()` utility the same way every other storage failure in `App.tsx` already is.
- **[The 1.2s / 70-30 split and the hour-bucket boundaries for the time-of-day phrase are unvalidated first-pass numbers]** — accepted, logged as such, cheap to retune, no economy stake either way.
- **[Four open copy/UX questions in `proposal.md` are recommended-default, not user-confirmed]** — doesn't block starting the rest of this change; only the specific lines/labels those questions touch would need a follow-up edit if the founder's answer differs from the recommended default.
