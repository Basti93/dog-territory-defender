## Context

Today, `expo-notifications` is **not** a project dependency — no notification of any kind (local or push) currently exists anywhere in the app. `openspec/specs/den-economy/spec.md`'s overflow requirement ("...the system SHALL notify the player when passive treat storage overflows") is currently satisfied only by in-app text/UI the player sees if and when they open the app — there is no mechanism that reaches them while the app is closed.

The existing reward path (treats, XP, personal stats, achievements) for a closed walk runs entirely from local state and local repositories (`src/storage/WalkRepository.ts`, `DenEconomyRepository.ts`, `PersonalStatsRepository.ts`) — no backend, no sync, matching the rest of the app. That reward logic is currently **inline inside `App.tsx`'s `stopWalk` closure** (`awardWalkTreats`, `recordWalkClosed`/`recordTreatsEarned`, `awardWalkXp`, celebration payload assembly, all called in sequence against `closedWalk`) — it is not already a separate, callable function. `Walk` (`src/types.ts`) is currently: `id`, `startTime`, `locations: Location[]`, `territory?`, `closed`. `territory` is already optional, which matters for a manually-logged walk that has no real GPS trail to derive a polygon from.

## Goals

- A notification fires only when a real, already-true, unclaimed Den-economy overflow condition exists — never a bare reminder invented on a clock.
- A player can log a walk the app missed, in one clear in-app action, and get the identical reward outcome (treats, XP, personal stats, achievements) a normally-closed tracked walk gets.
- Tracked (`button`) and manually-logged (`manual-log`) walks are distinguishable in storage, so a future analysis can tell whether this MVP moved walks/day.
- Notification permission is requested only at the point the player first does something that needs it (not at cold app launch), matching the app's general preference for asking for access only when it's actually about to be used.

## Non-Goals

- No home/lock-screen widget, no clock-fired "time to walk" reminder, no automatic walk detection/inference — all explicitly deferred per `proposal.md`.
- No notification tied to "Log a walk we missed" in this change. See Decisions below for why that trigger condition (present in `walk-start-experience`'s original MVP bullet) is dropped here.
- No new backend or sync layer. The earned-trigger check and the learned time-of-day bucket are both derived entirely from data already sitting in local storage (Den economy state, past walks) — no new server round-trip.
- No opt-in toggle/settings screen for this notification. Per `walk-start-experience`'s "Notification Timing (resolved)," an earned-trigger notification (fires only on something already true) is fun-safe to ship outright; the OS-level notification-permission prompt is the only consent surface needed here. (A settings toggle to mute it later is reasonable future polish, not required for this MVP.)
- No change to `canCloseWalk`'s thresholds or to how a live-tracked walk closes — untouched.

## Decisions

**New dependency: `expo-notifications`.** This is the one real scope-affecting choice in this change — no local-notification capability exists today. It's the standard Expo-managed path for local notifications and fits the existing all-Expo-SDK dependency list; no alternative was seriously considered given the project's managed-Expo-first stack.

**The "unclaimed manually-logged walk" earned-trigger condition is dropped from this MVP.** `walk-start-experience/proposal.md`'s MVP Scope bullet listed two trigger conditions for the earned-trigger notification: a Den-economy overflow, and "a manually-logged missed walk sitting unclaimed." The second is not implementable as specified: "Log a walk we missed" (below) awards its reward synchronously, the instant the player taps it, so a manually-logged walk is never in an unclaimed state a later notification could surface — by the time it exists in storage it has already been rewarded. Making that trigger real would require redesigning the button into a two-phase flag-now/claim-later flow (log an intent, confirm/claim it separately later) — genuine added scope, not a wiring detail, and not needed to test this change's actual hypothesis (does an earned-trigger notification plus a friction-free log button move walks/day). This change ships the notification driven by Den-economy overflow only; the manual-log button ships as a standalone, silent, one-step reward action with no notification tied to it. Revisit the two-phase redesign only if this MVP's data suggests the friction hypothesis needs it.

**A manually-logged walk must be capped to a short, recent look-back window — not an open-ended backfill.** Player-facing rationale: past a certain point, "logging a walk we missed" stops reading as "we just missed this" and starts reading as a general backfill tool, which invites gaming the treats/XP economy with walks that may not have happened as described. Concrete threshold: **the walk being logged must have started within the current or previous calendar day** (i.e., "earlier today" or "yesterday," not further back). This is a first-pass number, not empirically tuned — log it here as the numeric threshold decision per project convention, and revisit if real usage shows it's too tight or too loose.

**The existing closed-walk reward logic needs extracting into a shared, callable function before a manual log can reuse it.** It currently lives inline in `App.tsx`'s `stopWalk` closure, coupled to that function's local variables (`appState.walk`, `polygon`, `closedWalk`). "Reuse the reward path" for a manual log therefore means: extract that block into a function taking a `Walk` (plus derived `distanceMeters`/`areaM2`) and returning the updated Den economy state, personal stats result, and celebration payload — then have both `stopWalk` (tracked-walk closure) and the new manual-log handler call it. This is a small, contained refactor, not a redesign of the reward formulas themselves — `awardWalkTreats` is location-independent (a flat per-walk amount) and applies unchanged; `awardWalkXp`'s formula has a flat per-walk base component plus distance/area terms, and a manually-logged walk has no real GPS trail, so distance and area are both zero, and the player still receives the base XP.

**Named tension, not resolved here:** `walk-start-experience`'s guardrail is that a retroactively-claimed walk must never read as lesser — no reduced reward, no "unverified" label — but the concept's "route filled in... same green territory-claiming payoff" language assumed the *automatic* detection variant (deferred), where a real route exists to draw. A manual log has no real route, so no territory polygon can honestly be produced. The reward numbers stay identical, but the celebration screen's presentation for a manual-log walk still needs a small explicit decision. In practice this is a narrower problem than it first sounds: `CelebrationScreen.tsx` is text-only today (no rendered polygon graphic anywhere — just an "`{areaM2} m² is now yours`" line, treats, tease, achievements, level), and `WalkHistoryScreen.tsx`'s rows are text-only too (date, closed/open status, point count). So the open decision is just what the area line (and possibly the title) says when `territory` is `undefined`, not a graphics problem. This needs a short game-master pass on the exact copy before it ships (see `tasks.md`) — flagged here rather than silently decided either way.

**Notification bookkeeping is new local state, not a reuse of an existing repository's shape.** Two small pieces of state need to persist locally: whether the current Den-economy overflow has already been surfaced (so the same overflow doesn't fire a duplicate notification every day it stays unclaimed — confirmed there's no existing flag for this; `DenScreen.tsx`'s in-app overflow notice is computed fresh each render from `treats >= storageCap`, nothing persisted today), and the learned coarse time-of-day bucket (derived from past walk start times in `WalkRepository`, recomputed as more walks accumulate). Exact schema is an implementation choice — follow the existing repository-pattern convention (`interface` + `sqlite*Repository` + `inMemory*Repository`, per `src/storage/`) rather than bolting this onto `DenEconomyRepository` or `WalkRepository`'s existing shape.

**Notification permission is requested lazily.** Ask for OS notification permission the first time it's actually needed — when the earned-trigger check is first about to schedule/send one. (The manual-log flow itself no longer needs notification permission, per the scope cut above — it's a plain in-app action.) Not at app launch, matching the project's general stance of not front-loading permission asks before they're relevant (mirrors `background-location-tracking`'s location-permission-at-first-use pattern).

**The earned-trigger check runs off existing local reads only.** No new "walk detection" logic — it reads whatever `DenEconomyRepository` already knows (Den economy state that has hit its storage cap since it was last surfaced) plus the new notification-bookkeeping state, and decides fire-or-silent from that single condition. This keeps the notification honest to the "already true" rule by construction — there's no code path that invents a condition to report.

## Risks / Trade-offs

- [The territory-polygon tension above (manual-log walks can't have a real claimed-ground visual) is a genuine, not-yet-fully-resolved edge case against the "never lesser" guardrail] → Flagged explicitly rather than papered over; needs a short design pass on the celebration screen's copy before this ships, not blocking the rest of the change.
- [Cutting the manual-log earned-trigger condition means this change ships less of `walk-start-experience`'s originally-scoped MVP bullet than first proposed] → Accepted; documented explicitly as a scope cut with rationale rather than silently narrowed. A two-phase flag-then-claim redesign remains available as a separate, later change if data supports it.
- [Local notifications alone, with no backend, mean the earned-trigger check can only run while the app has been opened recently enough to compute it and schedule ahead — there's no server waking the app to check on a currently-closed app] → Accepted for this MVP; matches the no-backend architecture everywhere else in the app. The executing developer should pick a check cadence (e.g., recomputed and (re)scheduled each time the app opens or backgrounds) that's honest about this constraint rather than promising same-day delivery no matter what.
- [A calendar-day look-back cap is a coarse, first-pass number, not derived from real player behavior] → Accepted; it's a starting point, not a proven-correct threshold — revisit if real usage surfaces it as wrong in either direction.
