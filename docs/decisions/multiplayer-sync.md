# Multiplayer household sync + neighbour dogs (2026-10-18, M1-M4 shipped, M5+ open)
**Why:** Everything was local to one phone. Owner and partner share one dog (Android + iPhone): one Buddy, one Home Range, one Den. Smallest real multiplayer; forces accounts, sync, conflicts, hosting, privacy to be solved for 2 trusted users before strangers. Social layer (other real players, leaderboards) NOT built.
**Decisions:**
- Model: household (1 dog, 1..4 players, `HOUSEHOLD_MAX_PLAYERS`, tested with 2); each phone = device with own bearer token. Household creation = operator CLI over ssh only; no admin endpoint/token on HTTP.
- Stack: `server/` (own package.json, no workspace): Node 22, Fastify 5, TypeBox, Drizzle + Postgres 16, vitest. Fastify over Hono (Node-first, built-in validation); Drizzle over Prisma (no Rust engine, api budget 384 MiB); Postgres over SQLite for cloud parity + `SELECT ... FOR UPDATE` on `den_state`.
- Shared code: contract `src/sync/apiContract.ts` imported by server by relative path; server also imports pure economy/grid files (allowlist in `server/README.md`, purity test `src/sync/__tests__/sharedPurity.test.ts` fails on RN/expo/i18n imports). Same numbers, one definition.
- Authority: walks append-only (client UUID, soft delete, cells never un-painted); cells derived on server; territories server-authoritative; Den state (treats, XP, level, buildings, manual-log counters) server-authoritative via idempotent commands (`clientId` in `command_log`; `walk.finish`, `walk.manualLog`, `den.upgrade`, `walk.delete`, `dog.update`, `player.rename` 1-24 chars, `gift.open`). Dog name last-writer-wins. Settings stay per device; personal stats/achievements move to the server per player (plan below).
- Reward: server recomputes; local estimate shown instantly, server number wins quietly; rejected upgrade (`insufficient-treats`) rolls back with a gentle line.
- Cells: server keeps `cell_days(household,ix,iy,day)`; `visits = baseline_visits + count(days)` (household timezone). Union of days is commutative/idempotent and keeps the once-per-cell-per-day cap household-wide. Client applies `max` per field via `HomeRangeRepository.mergeCells`.
- Anti-snowball: Beginner's Luck keyed to household creation date; manual-log quota (2/day, 1 route refresh/day) household-wide; no "more members" bonus.
- Feed: one append-only `events` table (seq cursor) = change feed + Doorstep feed. `GET /v1/events?after&wait<=25s` long-poll (RN has no EventSource), `GET /v1/snapshot` to bootstrap. Time: `serverTime`, `clockOffsetMs`; walks >5 min future or >30 days old rejected.
- Client (`src/sync/`): SQLite `sync_outbox`, foreground-only sync, backoff 5 s to 5 min, 15 s fetch timeout, no background tasks/NetInfo (native deps). Token unencrypted at rest (accepted; `expo-secure-store` before public release), never in Backup JSON. Restore disabled while joined.
- Auth: single-use invite (8 chars, 24 h, hashed), `POST /v1/join`; token 32 random bytes, SHA-256 stored; swappable `Authenticator` seam for later OIDC.
- Hosting: home server, compose project `dog-territory` (api 384m, db 512m, tailscale sidecar 128m = 1 GiB), 127.0.0.1:7000/7001. Public via Tailscale Funnel on own sidecar node `your-server.example.com:443` (owner decision: no Tailscale on phones). Backups: daily 06:30 pg_dump, 14 days (never 02:00-06:00).
- Hardening (Decision 16): only `GET /healthz` + `POST /v1/join` unauthenticated, everything else 401 incl. unknown paths; join 5/min and 20/day per IP, global 100/h; 120 req/min per token; 30/min unauth per IP; `banned_ips` (10 fails/10 min = 1 h, doubling to 24 h); bodyLimit 64 KiB; JSON only; helmet, no CORS; 200 commands + 50 walks/day per household; logs never hold tokens/coordinates; IP logs ~14 days; kill switch `docker compose stop api` (app is offline-first).
- Privacy: members see each other's full routes (consent tap, `players.consented_at`); anything cross-household needs 100 m start fuzz; `DELETE /v1/me`, `DELETE /v1/household`. Needs privacy policy, DPIA, legal check before any non-test user.
- Track B "Nachbarhunde" (bots, `NEIGHBOURS_ENABLED`, default true in `deploy/docker-compose.yml`, enable only when both phones have the build): six bot households (`is_bot`; Momo, Pfote, Bruno, Keks, Lotte, Nebel) created at host's first tracked walk; routes generated from OSM ways (Overpass, ~2 km tiles cached in `street_tiles`, loops within +-20 % of target, home block `HOME_BLOCK_RADIUS_M` 150 m excluded; fallback = offset copies of host's last 10 walks 300-1500 m). Never go through `walk.finish`; no territories, no Den. Tunables in `src/economy/neighbourConfig.ts`, archetypes in `server/src/neighbours/archetypes.ts`.
- Bot rules: max 2 events/day, 1 gift/day, 1 invitation/ISO week, 3 reactions/week, no `line_key` repeat in 10 days; escalation W1 Momo+Pfote, W2 Bruno, W3 Keks+Lotte+first Viertel-Runde, W4 Nebel. Gift sprinkle `SPRINKLE_FRACTION` 5 % of avg treats over last 14 human walks, credited on `gift.open`, outside the +30 % power budget. Viertel-Runde goal G = B + P (P 4-12 km, B <= 60 % of G, effectively ~10-30 km), no loss state, carry-over up to 50 % of next P, reward yard decoration. Bots are openly "simuliert" (paw-robot badge on the card only).
- Presence (M4): ephemeral `walk_presence` table + `POST/GET /v1/presence` (not in `events`); beat ~30 s, 1 req/10 s per device, <=400 points, purged after 6 h, viewer long-poll foreground only, stale after 3 min. Live share is opt-in (default off, `liveShareEnabled`). Late mini-homecoming: one per app open, partner walk <48 h.
- Ops: `API_LEVEL = 2` (`X-Api-Level`, 426 on writes below `MIN_CLIENT_API_LEVEL`), additive-only changes, unknown event kinds ignored; `deploy/restore-drill.sh`, `BACKUP_COPY_DIR`/`BACKUP_RSYNC_TARGET`.
**Rejected:** client LWW for all (wrong for spendable balance, territories fork); CRDTs (overkill); SSE/WebSockets (no RN EventSource, background kills sockets); Prisma, SQLite-on-server, npm workspaces; OSRM/Valhalla (multi-GB extract on a 7.1 GiB shared host); Tailscale on phones (superseded by Funnel); admin token over HTTP; fail2ban (no OS changes); per-screen refetching of neighbour data; persisting the presence buffer (walk dies with the process anyway); push (iPhone free team has no APNs).

## Plan: personal stats on the server, identity ready for Google/Apple sign-in (2026-10-18, NOT built, needs owner go for server deploy)
**Why:** Walks, cells, territories, Den, dog, corners are already on the server (restorable by re-joining). Only these live solely on the phone: `PersonalStatsState` (7 lifetime numbers, `src/economy/personalStats.ts`) and the unlocked achievements with dates (`PersonalStatsRepository`). Deleting the app loses them (and the fence badges derived from them); local Backup JSON (`src/storage/backup.ts`) is manual and disabled while joined. Everything else in the backup is either already synced (walks, cells, territories, Den subset, dog name/look, player name) or device-local on purpose (below). Reverses "stats stay local" for storage only: visibility is unchanged (per player, never shown to partners or others, never compared; `personal-stats.md`, `anti-snowball.md`).
**Decisions, data:**
- Store per `player_id` (not household, not device): table `player_stats(player_id PK -> players ON DELETE CASCADE, stats jsonb, updated_at)` and `player_achievements(player_id, achievement_id, unlocked_at, PK both)`, migration `0007_player_stats.sql` (0006 corners is still uncommitted; 0007 follows it and may ship together). jsonb because the stat list will grow; the merge is generic over keys.
- Source of truth = client snapshots with monotonic merge, NOT server recompute: passive-treat income, Den-building achievements and the pre-2026-10-18 distance totals ("never recomputed or lowered", `personal-stats.md`) cannot be derived from walks. Merge (`mergeStats`, pure, new `src/sync/statsMerge.ts` with structural types only; it must not import `personalStats.ts` because that pulls i18n; add to the allowlist in `server/README.md`, covered by `sharedPurity.test.ts`): every numeric key = max, `firstWalkAt` = min of non-null, achievements = union by id with the earliest `unlockedAt`. Commutative, idempotent, so retries, two devices and out-of-order requests are safe. Server ignores no data: unknown achievement ids (pattern `^[a-z0-9-]{1,40}$`, max 100) are kept, so a newer app's badges survive an older server/app.
- Not an economy command and no event: personal data must not enter the household-wide `events` feed or `economy_commands` (den lock, 200/day cap). New `PUT /v1/me/stats` (`API_PATHS.meStats`), body `{stats, achievements}` strict schema, finite numbers 0..sane caps, response = merged result; row lock on the player's stats row. Snapshot gets additive `myStats?` (the caller's own only; partners' stats are never serialised anywhere).
- Client (`src/sync/`, new `statsSync.ts`, driven by `syncEngine.ts`): no outbox row. A dirty flag (local state differs from last uploaded) triggers a PUT of the FULL current state at most once per 60 s and on foreground; a lost request costs nothing. On join/cold start the snapshot's `myStats` is max-merged into the local repo silently (no homecoming, no badge arrival). Upload waits until the first snapshot after join is applied, so a fresh install never writes counters that the merge would then hide (a walk finished before the pull would be absorbed by max; accepted, join comes before the first walk). A second phone of the same player loses its smaller increments to max; accepted (one active phone per player); a per-device counter sum was rejected as too heavy.
- Migration of today's local data = the first PUT after the app update (local state against an empty server row merges to local). No `--allow-import` / founding-import involvement; the import stays walks/cells/Den only. Both existing players upload with their own token.
- Restore on a fresh install needs the SAME `player_id` (a normal join creates a new player and the stats would have no owner). `invite_codes` gets nullable `player_id`; operator CLI `create-invite --household H --for-player <name|id>`. Joining with it inserts only a `devices` row for that player (no `member.joined`, no capacity check, consent already stored), then the normal snapshot restores walks, Range, Den, dog, corners and stats. The old device is revoked with `revoke-device`. One server function `attachDevice(playerId, label)`; the later sign-in restore reuses it.
- Server backup: nightly pg_dump already includes the new tables; add `player_stats` to the counts in `deploy/restore-drill.sh`. The server becomes the only copy of restorable progress, so before telling anyone "reinstall is safe" turn on the off-disk copy (`deploy/mac/install-pull.sh` is the Mac pull, or `BACKUP_COPY_DIR`) and run `make restore-drill` after the migration.
- Stays local, by design: language and `onboardingDone` (restored flow must skip onboarding when joined: test), `FeedbackPrefs` (sound/haptics), notification bookkeeping (OS permission is per device), `liveShareEnabled` (consent is asked per phone), shown-homecoming ids, `cliffhangerShownForLevel`, backfill flags, `newGroundEvent`, outbox, token. None is worth a restore; revisit a `players.prefs` jsonb only if an account profile needs language.
**Decisions, identity (design now, build later):**
- Tables for the later slice (NOT in 0007): `accounts(id uuid PK, created_at, deleted_at)` and `account_identities(provider 'apple'|'google', subject, account_id -> accounts, email nullable, PK(provider, subject))`; `players.account_id uuid NULL -> accounts` (1 account : n players, one per household). Household membership, consent and all game data stay on `players`; `devices` stay the session credential. Stats are keyed on `player_id` today; an account profile is later the merge over `players WHERE account_id = X`, which works unchanged because the merge is commutative. No stats column ever keys on a device or on an account.
- Linking an existing invite-joined player: signed in with the device token, `POST /v1/me/link {provider, idToken}` sets `account_id`; no data moves. Sign-in on a fresh install: verify the provider ID token (JWKS, `aud`, `nonce`, expiry; pure-JS `jose`), find the account, `attachDevice` to its player, same restore as above, no operator step. Never merge accounts by email (takeover risk); the email is optional, may be Apple's private relay, and is never a key.
- Sits behind the existing `Authenticator` seam (`server/src/http/auth.ts`); routes, commands and tables do not change. Stay portable: standard Postgres, uuid keys, no provider SDK on the server, no host names in data.
- Rules to meet before any public user: Sign in with Apple is mandatory once Google (or another social login) is offered (App Store 4.8); in-app account deletion (App Store 5.1.1(v), Google Play account-deletion policy incl. a web link) and, for Apple identities, revoking the Apple token on delete; privacy policy and store data-safety/nutrition labels. `DELETE /v1/me` and `DELETE /v1/household` are listed under Privacy above but NOT implemented (checked `server/src/http/app.ts`). The new tables cascade from `players`; `walks.player_id` has no `ON DELETE` rule and must become `SET NULL` or be anonymised first. Verify current store wording when implementing.
- Not now: OAuth, Google/Apple SDKs and any new native dependency (each forces a dev-client rebuild; owner go-ahead), `accounts` tables, a login screen.
**API contract:** additive inside `API_LEVEL = 2` (no bump, no `MIN_CLIENT_API_LEVEL` change): `API_PATHS.meStats`, `ApiPersonalStats`/`ApiMyStats`, `SnapshotResponse.myStats?`, strict TypeBox in `server/src/http/schemas.ts`, no new command and no new `EventKind`. App on a server without the route gets an authenticated 404: mark stats sync unsupported for the session, keep playing. Old app on new server is unaffected. Update `server/README.md` (endpoint, CLI flag, allowlist), `src/sync/apiContract.ts` doc comment ("Additive inside level 2"), `docs/specs/personal-stats.md` (the fence line "this device only, never synced" becomes "stored per player on the server for restore, never shown to others"), README status, LOG.md.
**Tests:** pure `mergeStats` (commutative, idempotent, never lowers, min date, unknown ids kept); server (PGlite): migration 0007 on top of 0006, PUT validation (negative, NaN, huge, bad id, 101 ids, unknown key), two PUTs in any order give one result, player A's data is absent from B's snapshot and writes no `events` row, `--for-player` join reuses the player id, adds no `member.joined`, ignores capacity and the code stays single-use, cascade on player delete; app: snapshot merge never lowers local stats and raises no celebration, upload only when dirty, 404 handling, restore flow skips onboarding. Owner checks on device: reinstall with a for-player invite shows badges and totals again.
**Rollout:** (1) owner says "deploy" (nothing on the server before that); `make backup`, deploy per `deploy/README.md` (build, `make migrate`, `up -d`; 0006 and 0007 together) and `make restore-drill`; (2) only then `eas update` (JS only, no native change, same runtime); (3) first open of each phone uploads its stats; check with the owner that both players' rows exist; (4) restore rehearsal with a spare install and a `--for-player` invite; (5) accounts slice later as its own plan.
**Risks:** a client bug that inflates a stat is permanent (monotonic by design; operator `reset-stats --player` as escape hatch, add to the CLI); single-host DB until the off-disk copy runs; the invite-for-player code is a takeover path for a household's player, hence operator-only, 24 h, single-use, same as invites today; Apple/Google policy details drift, re-check at implementation.
