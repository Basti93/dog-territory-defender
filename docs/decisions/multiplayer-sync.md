# Multiplayer household sync + neighbour dogs (2026-10-18, M1-M4 shipped, M5+ open)
**Why:** Everything was local to one phone. Owner and partner share one dog (Android + iPhone): one Buddy, one Home Range, one Den. Smallest real multiplayer; forces accounts, sync, conflicts, hosting, privacy to be solved for 2 trusted users before strangers. Social layer (other real players, leaderboards) NOT built.
**Decisions:**
- Model: household (1 dog, 1..4 players, `HOUSEHOLD_MAX_PLAYERS`, tested with 2); each phone = device with own bearer token. Household creation = operator CLI over ssh only; no admin endpoint/token on HTTP.
- Stack: `server/` (own package.json, no workspace): Node 22, Fastify 5, TypeBox, Drizzle + Postgres 16, vitest. Fastify over Hono (Node-first, built-in validation); Drizzle over Prisma (no Rust engine, api budget 384 MiB); Postgres over SQLite for cloud parity + `SELECT ... FOR UPDATE` on `den_state`.
- Shared code: contract `src/sync/apiContract.ts` imported by server by relative path; server also imports pure economy/grid files (allowlist in `server/README.md`, purity test `src/sync/__tests__/sharedPurity.test.ts` fails on RN/expo/i18n imports). Same numbers, one definition.
- Authority: walks append-only (client UUID, soft delete, cells never un-painted); cells derived on server; territories server-authoritative; Den state (treats, XP, level, buildings, manual-log counters) server-authoritative via idempotent commands (`clientId` in `command_log`; `walk.finish`, `walk.manualLog`, `den.upgrade`, `walk.delete`, `dog.update`, `player.rename` 1-24 chars, `gift.open`). Dog name last-writer-wins. Settings stay per device; personal stats/achievements move to the server per player (last section).
- Reward: server recomputes; local estimate shown instantly, server number wins quietly; rejected upgrade (`insufficient-treats`) rolls back with a gentle line.
- Cells: server keeps `cell_days(household,ix,iy,day)`; `visits = baseline_visits + count(days)` (household timezone). Union of days is commutative/idempotent and keeps the once-per-cell-per-day cap household-wide. Client applies `max` per field via `HomeRangeRepository.mergeCells`.
- Anti-snowball: Beginner's Luck keyed to household creation date; manual-log quota (2/day, 1 route refresh/day) household-wide; no "more members" bonus.
- Feed: one append-only `events` table (seq cursor) = change feed + Doorstep feed. `GET /v1/events?after&wait<=25s` long-poll (RN has no EventSource), `GET /v1/snapshot` to bootstrap. Time: `serverTime`, `clockOffsetMs`; walks >5 min future or >30 days old rejected.
- Client (`src/sync/`): SQLite `sync_outbox`, foreground-only sync, backoff 5 s to 5 min, 15 s fetch timeout, no background tasks/NetInfo (native deps). Token unencrypted at rest (accepted; `expo-secure-store` before public release), never in Backup JSON. Restore disabled while joined.
- Auth: single-use invite (8 chars, 24 h, hashed), `POST /v1/join`; token 32 random bytes, SHA-256 stored; swappable `Authenticator` seam for later OIDC.
- Hosting: home server, compose project `dog-territory` (api 384m, db 512m, tailscale sidecar 128m = 1 GiB), 127.0.0.1:7000/7001. Public via Tailscale Funnel on own sidecar node `your-server.example.com:443` (owner decision: no Tailscale on phones). Backups: daily 06:30 pg_dump, 14 days (never 02:00-06:00).
- Hardening (Decision 16): only `GET /healthz` + `POST /v1/join` unauthenticated, everything else 401 incl. unknown paths; join 5/min and 20/day per IP, global 100/h; 120 req/min per token; 30/min unauth per IP; `banned_ips` (10 fails/10 min = 1 h, doubling to 24 h); bodyLimit 64 KiB; JSON only; helmet, no CORS; 200 commands + 50 walks/day per household; logs never hold tokens/coordinates; IP logs ~14 days; kill switch `docker compose stop api` (app is offline-first).
- Privacy: members see each other's full routes (consent tap, `players.consented_at`); anything cross-household needs 100 m start fuzz; `DELETE /v1/me`, `DELETE /v1/household`. Needs privacy policy, DPIA, legal check before any non-test user.
- Track B "Nachbarhunde" (bots, `NEIGHBOURS_ENABLED`, default true in `deploy/docker-compose.yml`, enable only when both phones have the build): six bot households (`is_bot`; Momo, Pfote, Bruno, Keks, Lotte, Nebel) created at host's first tracked walk; routes generated from OSM ways (Overpass, ~2 km tiles cached in `street_tiles`, loops within +-20 % of target, home block `HOME_BLOCK_RADIUS_M` 150 m excluded; fallback = offset copies of host's last 10 walks 300-1500 m). Never go through `walk.finish`; no territories, no Den. Tunables in `src/economy/neighbourConfig.ts`, archetypes in `server/src/neighbours/archetypes.ts`.
- Bot rules: max 2 events/day, 1 gift/day, 1 invitation/ISO week, 3 reactions/week, no `line_key` repeat in 10 days; escalation W1 Momo+Pfote, W2 Bruno, W3 Keks+Lotte+first Viertel-Runde, W4 Nebel. Gift sprinkle `SPRINKLE_FRACTION` 5 % of avg treats over last 14 human walks, credited on `gift.open`, outside the +30 % power budget. Viertel-Runde goal G = B + P (P 4-12 km, B <= 60 % of G, effectively ~10-30 km), no loss state, carry-over up to 50 % of next P, reward yard decoration. Bots are openly "simuliert" (paw-robot badge on the card only).
- Presence (M4): ephemeral `walk_presence` table + `POST/GET /v1/presence` (not in `events`); beat ~30 s, 1 req/10 s per device, <=400 points, purged after 6 h, viewer long-poll foreground only, stale after 3 min. Live share is opt-in (default off, `liveShareEnabled`). Late mini-homecoming: one per app open, partner walk <48 h.
- Ops: `API_LEVEL = 2` (`X-Api-Level`, 426 on writes below `MIN_CLIENT_API_LEVEL`), additive-only changes, unknown event kinds ignored; `deploy/restore-drill.sh`, `BACKUP_COPY_DIR`/`BACKUP_RSYNC_TARGET`.
**Rejected:** client LWW for all (wrong for spendable balance, territories fork); CRDTs (overkill); SSE/WebSockets (no RN EventSource, background kills sockets); Prisma, SQLite-on-server, npm workspaces; OSRM/Valhalla (multi-GB extract on a 7.1 GiB shared host); Tailscale on phones (superseded by Funnel); admin token over HTTP; fail2ban (no OS changes); per-screen refetching of neighbour data; persisting the presence buffer (walk dies with the process anyway); push (iPhone free team has no APNs).

## Personal stats on the server, identity ready for Google/Apple sign-in (2026-10-19, built, server deploy pending the owner's go; accounts are design only)
**Why:** Walks, cells, territories, Den, dog name, corners are on the server (restorable by re-joining). Only `PersonalStatsState` (7 lifetime numbers, `src/economy/personalStats.ts`) and the unlocked achievements with dates lived solely on the phone; deleting the app lost them (and the fence badges). Reverses "stats stay local" for storage only: visibility is unchanged (per player, never shown to partners or others, never compared; `personal-stats.md`, `anti-snowball.md`).
**Built (data, server):**
- Per `player_id` (not household, device or account): `player_stats(player_id PK -> players ON DELETE CASCADE, state jsonb, updated_at)` and `player_achievements(player_id, achievement_id, unlocked_at, PK both)`, migration `0007_player_stats` (ships with 0006). Unknown achievement ids are kept (pattern `^[a-z0-9-]{1,40}$`, 100 per PUT, 200 stored per player, then 400).
- Client snapshots with monotonic merge, NOT server recompute (passive treats, Den-building badges and pre-2026-10-18 distance totals cannot be derived from walks). `mergeStats` in `src/sync/statsMerge.ts` (pure, no imports, test-enforced): numbers = max, `firstWalkAt` = earliest non-null, achievements = union with earliest date. Commutative and idempotent, so retries, two phones and out-of-order requests are safe.
- `PUT /v1/me/stats` (`API_PATHS.meStats`): full state in, merged state out, row lock on the player's row, strict schema (finite 0..caps in `STATS_CAPS`, ms times rounded by `normalizeMyStats` like walks, unknown stat key = 400). Not an economy command: never an `events` row, never `economy_commands`. `SnapshotResponse.myStats?` = the caller's own only.
- Restore: `invite_codes.player_id` (nullable); CLI `create-invite --for-player <id|name> [--household H]`; join with it calls `attachDevice(playerId, label)` (device row only: no `member.joined`, no capacity check, no rename, consent already stored), single-use, 24 h, `JoinResponse.restored` + `playerName`. The old device is revoked with `revoke-device`.
**Built (app, `src/sync/statsSync.ts`, driven by `syncEngine.ts`):** no outbox row. "Dirty" = local state differs from what the server last confirmed (derived, so every writer is covered). Upload of the FULL state at most every 60 s, at once on foreground/launch/manual sync, only after a successful pull (so after a join the first snapshot's `myStats` is merged first, silently: no homecoming, no badge arrival). The PUT answer is merged back too (second phone). Ids the app cannot draw stay on the server only. A 404/400/426 from the route (older server) stops uploads until the next app start; offline is quiet. A restored join adopts the stored player name and sets `onboardingDone`. A second phone of the same player can lose small increments to max (accepted, one active phone per player). A founding import is not involved; today's local data goes up with the first PUT after the update.
**Checked while building:** joining is only reachable from Settings, i.e. after onboarding, so a reinstall still walks the cards and names a dog first; the snapshot then overwrites the dog NAME, but the dog LOOK is not restored (nothing writes or applies `dog.appearance` after the founding import). Follow-ups: a "restore" entry on the first onboarding card, and syncing the look.
**Stays local, by design:** language, `onboardingDone` (restored join sets it), `FeedbackPrefs`, notification bookkeeping, `liveShareEnabled`, shown-homecoming ids, `cliffhangerShownForLevel`, backfill flags, `newGroundEvent`, outbox, token.
**Identity (design only, NOT in 0007):** later tables `accounts(id uuid PK, created_at, deleted_at)` and `account_identities(provider 'apple'|'google', subject, account_id, email nullable, PK(provider, subject))`; `players.account_id uuid NULL` (1 account : n players, one per household). Stats stay keyed on `player_id`; an account profile is the merge over `players WHERE account_id = X` (works because the merge is commutative). Linking: `POST /v1/me/link {provider, idToken}` with the device token, no data moves. Sign-in on a fresh install: verify the ID token (JWKS, `aud`, `nonce`, expiry; pure-JS `jose`), find the account, `attachDevice`, same restore, no operator step. Never merge accounts by email. Sits behind the `Authenticator` seam; stay portable (standard Postgres, uuid keys, no provider SDK). Before any public user: Sign in with Apple once Google is offered (App Store 4.8), in-app account deletion (5.1.1(v), Google Play policy) incl. revoking the Apple token, privacy policy and store labels. `DELETE /v1/me` / `DELETE /v1/household` are NOT implemented; `walks.player_id` has no `ON DELETE` rule and must become `SET NULL` or be anonymised first. Not now: OAuth, provider SDKs, native deps, login screen.
**Rollout:** (1) owner says "deploy": `make backup`, deploy per `deploy/README.md` (build, `make migrate`, `up -d`; 0006 and 0007 together), `make restore-drill` (now also prints `player_stats`); (2) only then `eas update` (JS only); (3) first open of each phone uploads its stats, check both players' rows exist; (4) restore rehearsal with a spare install and a `--for-player` invite; (5) turn on the off-disk backup copy before telling anyone "reinstall is safe" (the server is now the only copy of restorable progress); (6) accounts slice later as its own plan.
**Risks:** a client bug that inflates a stat is permanent (monotonic by design; a `reset-stats --player` CLI command is NOT built yet, edit the row by hand); single-host DB until the off-disk copy runs; a restore invite is a takeover path for a player, hence operator-only, 24 h, single-use; a phone that leaves a household and joins as another player would upload its stats to the new player (same person, accepted); store policy details drift, re-check at implementation.
